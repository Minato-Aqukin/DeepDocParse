# DDP-Extract v1 —— 结构化抽取结果格式

`/v1/extract/{task_id}/result` 与 Web 层 `/api/extractions/{run_id}` 返回的就是这个格式。

这份格式要回答的问题只有一个：**这个字段的值，是从原件的哪一块抽出来的？**
抽取产品普遍只给「字段 + 置信度」，指不回原文——本项目把出处从 chunk 级下沉到**字段级**，
差异化全押在这里。

- 共享格式与字段选择协议：`python/ddp_core/ddp_core/extract_format.py`。
- 抽取编排：`services/model-gateway/ddp_gateway/services/extraction.py`
  与 `services/corpus-api/ddp_corpus/extraction.py`；两端共用字段提示和选择校验。
- 对外仍为 DDP-Extract v1；内部模型选择协议单独版本化，不改变已保存结果。

## 输入：受限的 JSON Schema

**刻意只支持 JSON Schema 的一个子集。** 支持的：

```jsonc
{
  "type": "object",              // 或 "array"（多记录/表格抽取）
  "properties": {
    "buyer_name": {
      "type": "string",
      "description": "买方（甲方）单位全称"   // ← 同时是检索 query 与抽取提示，写清楚很值钱
    },
    "total_amount": { "type": "number", "description": "价税合计金额，只要数字" },
    "signed_at":    { "type": "string", "format": "date", "description": "合同签订日期" }
  },
  "required": ["buyer_name"]
}
```

| 支持 | 说明 |
|---|---|
| 顶层 `type: object` + `properties` | 单记录抽取（合同、发票、报告封面） |
| 顶层 `type: array` + `items.properties` | 多记录抽取（表格行、条目清单） |
| 叶子 `type`：`string` / `number` / `integer` / `boolean` | 值会按类型强制转换，转不动判 `error` |
| `format`：`date` / `date-time` / `email` / `uri` | 仅作抽取提示与格式校验，不做时区换算。**`uri` 只作提示，不校验**（URL 的合法形态太多，正则校验会误杀） |
| `description` | **最重要的一项**：它就是这个字段的检索 query |
| `enum` | 值必须落在枚举内。**越界判 `error` + `schema_violation`**，不是 `not_found` —— 模型给了一个枚举外的值是"它答错了"，不是"文档里没有"。不许把没有的选项硬塞一个 |
| `required` | 缺了它整体 `status` 降为 `partial` |

**明确不支持**（不是没来得及做，是刻意的）：

| 不支持 | 为什么 |
|---|---|
| 嵌套 object（`properties` 里再套 object） | 每加一层嵌套，检索次数与出处归属的歧义都乘一次。拍平写成 `buyer.name` 这样的扁平键 |
| `oneOf` / `anyOf` / `allOf` / `$ref` | 分支语义没法映射到「一个字段一次定位」，出处会指到多个互斥的块 |
| 数组套数组 | 同上 |
| 无 `description` 的字段 | **会被拒绝**：没有 description 就只能拿字段名当 query，`f1`/`amt` 这种名字检索必然打偏，而失败会表现为"抽不到"，看起来像模型不行 |

## 输出

```jsonc
{
  "extract_version": "ddp-extract/1",
  "doc_hash": "9f2c…",              // 文档身份（ADR #11），与解析平面同一个键
  "status": "ok",                    // ok | partial | failed
  "degraded": null,                  // 整体降级标记，取值见下表
  "fields": {                        // 顶层是 object 时用这个
    "buyer_name": {
      "status": "found",             // found | not_found | error
      "value": "北京某某科技有限公司",
      "citations": [ /* 见下 */ ],
      "verified": true,              // 做过视觉核对且一致
      "degraded": null,              // 字段级降级
      "confidence": {"level": "high", "top_similarity": 0.78, "warn_below": 0.60}
    },
    "total_amount": {
      "status": "not_found",         // 本次未找到值；不能据此断言整篇文档没有
      "value": null, "citations": [], "verified": false,
      "degraded": null, "confidence": {"level": "unknown", "top_similarity": null}
    }
  },
  "records": [ { "fields": { … } } ], // 顶层是 array 时用这个，元素形状与上面的 fields 一致
  "usage": {"fields": 12, "retrievals": 12, "chat_calls": 3}
}
```

### 字段三态（**这份格式最要紧的地方**）

| status | 含义 | 判据 |
|---|---|---|
| `found` | 抽到了值，且有出处 | 检索命中过相似度下限，模型从块里抽出了值；对象数值字段的字面来源检查见下，不等同语义核验 |
| `not_found` | **本次检索与抽取未找到值，不证明原文不存在** | 检索零命中，或模型明确回答未找到 |
| `error` | 没能抽成（系统/模型输出问题） | 类型转换失败、schema 校验不过、上游不可达、引用指针幻觉、数值无来源支持 |

**`not_found` 与 `error` 必须分开。** 前者是当前有界检索与抽取的结果，
后者是类型转换、schema、引用指针、数值核验或上游等系统/模型输出问题；两者都不能被翻译成“整篇文档没有”。
界面显示“本次未找到”，保留降级与核验状态，使用者可据原文继续复核。
评测中的「空值正确率」须用独立参考答案判定，不能把 `not_found` 自身当成正确标签。

**永远不许为了填满 schema 而编值。** 没有找到值可返回 `not_found`，
但检索漏召回、上下文截断或模型漏抽仍可能产生假阴性；状态不是全文覆盖证明。

### 引用指针与数值核验

对象字段的内部模型协议为 `ddp-field-selection/3`，只返回 `found`、`value`、`support`：
`{"found":true,"value":3,"support":{"value_source":9,"context_sources":[7]}}`。
`value_source` 明确指向包含值的资料，不能把原文阅读顺序误作值所在位置；
`context_sources` 明确选择最多两条主体/限定语资料。各编号均为 `1..N`
的整数形式（保留数字字符串的既有规则），不得重复、越界或使用布尔/小数。
坏形状、旧的并列指针/模型摘录、多余键或缺失字段均整体判
`error` + `schema_violation`；不猜值出处、不重排救援、不去重后放行、不挂 top-1。

对象字段模式的 `number` / `integer` 值在类型转换之后，还须在该编号提供给模型的
同份资料摘录中以数字形式出现；表格 HTML 或已标识的派生理解仍保留原有来源类型，
不能因本检查通过而称为“原文已核验”。千分位逗号、小数、科学记数法按精确十进制比较，
不通过浮点舍入或相对容差把两个不同值视为相同。句末逗号不属于数值，Unicode负号保留符号。
本检查不做单位换算、算术推导或文字数字解析；未能建立字面匹配判 `error` +
`schema_violation`，而非 `not_found`，不能由此推断文档没有该事实。
这只是机械约束，不构成含义/限定对象正确的证明；`string` / `boolean`
及多记录模式不应用此项额外检查。

类型转换与字面见证共用同一套数字记号写法：模型给的字符串值里恰好含一个
合法数字记号时才取值（两侧的千分位/小数/指数/Unicode 负号规则一致）。
带单位装饰的单数字回答（如 `"3 times"`）可取值；含零个或多个数字时
（如 `"−40∼105"` 区间）整体拒绝，不静默取第一个 —— 猜出来的值没法追溯。
转换还要求记号外没有未消费的正负号或不完整的指数：`"--40"`、`"1e-"`、`"1e"`、
`"e-40"` 及负号被币种隔开的 `"−$40"` 均拒绝，不截取子串或悄悄丢掉符号。
正常单位/币种装饰（如 `"$−40"`、`"3 pounds-force"`、`"1 eV"`）仍可解析。
紧邻 ASCII 标识符前缀的数字（如 `xP3`、`GPT-3`、`model_v3.2`）及点分版本号
（如 `3.5.2`）不作独立数量记号：数据源名称中的 `3` 不能证明“有 3 种语言”。
中文数量邻接（如 `共194种语言`）和正常后置单位（如 `0.3V`）仍保留；
这只是字面边界，不能把数值存在等同于主体、单位或所问范围成立。
`integer` 字段的大整数不经 float 中转，避免 2^53 以上精度丢失。
指数展开为整数之前检查十进制位数：不超过解释器默认安全上限；运行时上限更严时
使用更严的值，关闭运行时限制也不解除本检查。超限仍为 `CoerceError`，
不先分配巨型整数，也不把不能 JSON 序列化的值投影成 `found`。

字段 prompt 里“value 只放字段本身的值，不要带单位说明、不要带前后文”这一行
只适用于 `number` / `integer` / `boolean` 字段。`string` 字段的值本身可能就是
单位或名称（如 `tokens`），此时该行与字段含义自相矛盾，必须省略。

两端对象字段共用结构化提示：连续、同页同原始几何区域的片段分组阅读，
按原文顺序展示，但每个片段的资料编号与出处身份仍独立，不合并为假引文。
同一对象的其他字段定义只辅助消解请求范围，不作为文档证据。
一个字段明确要求多个分量时，须保留各分量及其对应关系；不能把原文已有的
中间分量静默删去，或用一个范围代替请求逐项列出的值。
涉及复合测量的字符串字段，还须保留请求中的量、单位、条件和限定语；
不能只摘出一列电流而省略同一请求中的功率，或只保留限值而删去适用条件。
这是生产指令，不是程序已经证明字段完整或事实正确。
模型显式选择值所在片段及必要的上下文片段；资料正文和出处身份从这些原件取得，
不再要求模型重抄一份 `evidence_excerpt`。这是选择协议，不是语义核验结论。
primary 必须陈述本字段请求的值及其主体：只复述相同数字、
主体却是另一事实的片段，或只吻合关联字段值的片段，
都不算包含本字段的值。
请求了位置的字段，若多处复述同一数值，须优先引用位置内的片段，
他处复述不是位置内引用。“that same \<位置\>”回指把 description 或
关联字段定义里点名的位置当作请求位置。
请求事实在同组连续片段间断句时，primary 仍选值所在的片段，
陈述请求主体/范围/第二事实的相邻片段走显式上下文引用：
同组阅读不等于同组引用。
中心字段检索同时保留“字段名＋描述”和独立描述两个有界表达；description 里
点名了位置（in the abstract、Table/Figure 编号、§/Section 编号、
中文“X 小节/章节/表/图”、“that same \<位置\>”回指中的位置名词）时
再加一条位置短语 leg（一字不改的原文搬运，只做召回、不作语义证明；
回指只搬位置名词本身）。最终候选数、固定版本与授权边界不变。
gateway 将这些去重后的检索词放在**一次** embedding 请求中，按响应 `index`
还原各查询的向量；缺失、重复、越界或类型错误的索引使整批显式降级为
`embedding_unavailable`，不能把另一查询的向量用作本查询的出处选择依据。
增加位置词 leg 不增加 embedding 请求次数；各路相似度下限和轮转候选上限不变。
中心对象字段启用重排时，在**同一候选池**内交错选择重排与混合召回的头部，
按“重排第1、召回第1、重排第2、召回第2……”去除已选身份后取原定种子数。
字段名式短查询可能把属性列名排在定义正文之前；仅作 RRF 共识融合又可能
同时挤掉两路各自前列的互补证据。该策略不增加候选池、种子数、模型调用
或上下文字符预算；原始相似度和重排分数分开保留，不把次序当置信度。
自然语言问答仍按其独立实测采用重排截断；不强制所有平面使用同一排名规则。
重排不可用仍显式降级并使用原召回顺序；多记录与 gateway 多路交错规则不变。
中心对象字段在原种子之后，先用至多与种子数相同的额外槽位保留同池中
下一批完整的连续同区域片段，再分配邻块；避免只扩展少数高排片段而丢掉
已经召回的定义正文。补入片段按原排名首次出现的顺序选择，同文档、解析版本、
页面、bbox、page_size 且序号连续才组成一个不可拆分的候选组；
组不能整体放进剩余字符/槽位时跳过，不靠截断或跨缺片拼接塞入。
总资料数仍不超过原种子数的三倍，字符预算、候选池与模型调用次数不增加；
该分配不能保证所有请求范围都被召回，也不构成语义核验。

邻块优先原始几何一致的续段，并在各命中间轮流分配预算，只追加完整原子。
同页 ±1 邻块之后，允许再带一条与该邻块原始 bbox/page_size 相同的连续原子，
以覆盖“标题→正文首片→同段续片”；不能越过缺片、页面、文档或解析版本。
额外原子总数仍不超过种子数的两倍，字符预算不变；不截断或伪造相似度。
位置词召回标题并不意味着完整正文已到达，超出这些边界的事实仍可能缺失。

### 显式值出处与上下文角色

`support.value_source` 是值所在片段；`support.context_sources` 是其他必要片段的
编号列表，没有额外限定语时必须为 `[]`。同一片段同时支持值和限定语，只选一次。
两侧都检查角色完整性、编号范围、唯一性和上限；不会改写模型指认来挽救失败。
`found=false` 必须同时配 `value=null`、`support=null`，非空选择不能冒充缺席。
数值见证始终只认显式 `value_source`，上下文仍不能抢救没有该数的值出处。
内部选择不再包含模型抄写的摘录，因此也不再把“模型重复的字符串出现在原文”
当额外一致性门控；它从来不等同含义/主体/单位的正确性证明。

两侧单字段请求使用同一 `json_schema`：必需封套字段、叶子值类型、可选枚举、
`1..N` 资料编号和最多两个 context 编号。原生支持的上游在解码时约束形状；
注册表显式声明 `options.structured_output: json_object` 的提供方复用网关既有适配器，
发送 JSON mode 并把 schema 放进提示词，**不声称具有解码级形状保证**。语料直连
`CHAT_URL` 时，上游须支持该 schema 协议；JSON-only 提供方应走已声明适配的网关。
这不增加重试、不抬高引用上限，也不把过长选择截短后接受。未声明的格式拒绝仍报
`upstream_error`，不在失败后偷偷切换协议。解码后的角色互斥、唯一性、缺席三元组、
类型转换与数值见证全部保留；结构合规不证明复合值完整或事实得到支持。

投影时 primary 在前、context 在后，只投影这些显式选择，不附带其余候选。
每条选中的出处独立走同一条裁剪+视觉核对（含预算/缓存记账）；
`verified=true` 要求每一条都真正核对过且一致，任一条没测出来/对不上，
整体即 `false`，降级标记按原有优先级如实透出。

原文与生成理解即使来自同一个 chunk，也各自占一个资料编号，只提供对应
`evidence_id` 的自有正文。选择生成理解不能借用附在它旁边的原文；
同时选择原文与生成理解时，落库不得按相同 `(parse_job_id, seq)` 把两者合成一个出处。
裁图像素可以复用，核对结果的缓存还必须区分 `evidence_id`，不能把原文的
核对结论传给生成理解。当前转写相似度只检查所选出处的图文一致性，
不证明抽取值、单位或行列对应正确，也不等同人工复核。
原文表格的核对使用其文字表示，而非 HTML 标签；生成视图仍只核对自己的生成正文。

### 多记录的内部资料选择

两端多记录生产协议为 `ddp-records-selection/1`：

```json
{"records": [{"source": 1, "values": {"item": "A", "quantity": 2, "source": "table-note", "values": 7}}]}
```

外层 `source` 是本次该块资料视图的 `1..N` 编号；用户定义的全部列放在
`values` 内，因此业务列仍可命名为 `source` 或 `values`，没有新增保留列名。
每一行只引用自己明确选中的资料视图，不因输入同时含原文和生成理解就自动挂两份支持。
缺失、越界的选择器，或缺失、非对象的 `values`，使该行被丢弃；
没有已有降级时标 `schema_violation`，已有降级按该路径的既有优先规则保留。
不接受旧的扁平生产行，也不根据输出值事后猜来源；其他合法行仍保留。
这是内部生产协议，公开结果仍为上面的 `records: [{"fields": ...}]`，不暴露该封套。


### 出处（citation）

形状与问答平面的 citation **完全一致**，前端 `CitationChip.vue` 不用改就能复用：

```jsonc
{
  "chunk_id": "…",        // 即时引用，reindex 后失效，不要存
  "parse_job_id": "…",    // 稳定定位键之一（service 侧为 null）
  "doc_hash": "…",        // service 侧的稳定定位键（Web 侧为 null）
  "seq": 3,               // 稳定定位键之二
  "page_idx": 2,          // 0 基页码
  "bbox": [72, 300, 540, 330],
  "page_size": [612, 792],
  "snippet": "…",
  "similarity": 0.78,     // 余弦相似度，有量纲。**不是 RRF 分**
  "crop_url": "…"         // 区域截图，可选
}
```

**稳定定位键是 `(parse_job_id, seq)`（Web 侧）/ `(doc_hash, seq)`（service 侧）**，
与问答平面同一套。理由见 ADR #11 与 P0：`chunk_id` 每次重建索引都会重铸，
只存它等于历史抽取结果一次 reindex 就永久失去原文依据。

### 降级标记

字段级 `degraded` 与整体 `degraded` 取值同一张表。前七种沿用问答平面，后三种是新增的：

| 值 | 含义 |
|---|---|
| `no_hits` | 检索零命中 |
| `embedding_unavailable` | 向量化不可用，只走了关键词路 |
| `vision_unavailable` | 视觉模型不可用，没做出处核对 |
| `crop_unsupported` | 非 PDF，裁不出区域图 |
| `crop_failed` | 能裁但渲染失败 |
| `parse_mismatch` | 裁出来的图与块文本对不上（解析本身可疑） |
| `upstream_error` | 上游模型报错 |
| **`schema_violation`** | **新增**：模型输出反复不合 schema，重试用尽；或引用指针幻觉（`source` 非 `1..N` 整数）；或数值无来源支持（所引块原文中找不到该数值） |
| **`rerank_unavailable`** | **新增**：配了精排但上游没注册 rerank 模型。照常返回融合名次，但如实说明没精排 |
| **`no_instruct_model`** | **新增**：注册表里没有会遵循指令的模型（只有 OCR 专用模型，或 `vqa_models` 为空），抽值无处可调 |

`no_instruct_model` 堵的是「抽取平面复用 VQA 平面的模型」这个设计的一个塌陷点：
VQA 位上放的若是 **OCR 专用模型**（DeepSeek-OCR 系），它只会把看到的字抄出来 ——
给它抽取指令，最好的结果是 `schema_violation`，最坏的结果是它吐出一个
能解析、但 `found=false` 的东西，于是**系统能力缺失伪装成了「文档里没有」**。
判据是注册表里的能力词：OCR 专用模型写 `capabilities: [vision, no_instruct]`，
抽值时跳过它们，视觉核对（原样抄写）照常用它们 —— 那正是它们的本行。

`schema_violation` 是抽取平面独有的洞：模型可以流利地输出一段**不是合法 JSON**、
或者字段名对不上、或者类型不对的东西。重试 `EXTRACT_MAX_RETRIES` 次仍不合规就打这个标，
**绝不静默丢弃该字段** —— 静默丢弃会让结果看起来像“文档里没有”。

### 邻块上下文（产品层字段抽取）

字段抽取允许在最终 `extract_candidates` 个命中之后，追加
`ddp_core.search.adjacent_context_hits` 返回的同页相邻块作为额外资料。
邻块保持各自独立的原子身份与 `evidence_id` / `bbox`（不与种子块合并成一条假引文），
在 prompt 里续编号并标注“相邻上下文（接续第 i 条）”，模型可引用其编号，
引用后可作为独立原子落库。邻块不挤占原命中名额，不参与相似度排序；
其 `similarity` 为 `None`（置信度如实 `unknown`），候选/审计层面须能区分邻接来源。
多记录（表格）抽取不扩展邻块。

## 自检

```python
from app.services import extract_format
problems = extract_format.validate_schema(user_schema)   # 返回问题清单，空 = 通过
problems = extract_format.validate_result(result)
```

`validate_schema` **在请求路径上强制**（与版面的 `validate` 不同）：
schema 是调用方给的输入，坏输入要当场 400 拒掉，而不是跑完一轮抽取再说。
`validate_result` 只在测试里是硬断言。
